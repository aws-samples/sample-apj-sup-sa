# Training XGBoost with MLflow autolog

This example runs a user Python script inside the SageMaker XGBoost container and shows how
`mlflow.xgboost.autolog()` automatically records training information.

```bash
./scripts/run-autolog-training.sh
```

## Can autolog be used with the built-in algorithm?

The SageMaker XGBoost container can be used in two ways.

| Mode | Training code | MLflow autolog |
|---|---|---|
| built-in algorithm mode | Training code provided by AWS | Not available, because there is no place to call it |
| framework or script mode | User-written `xgboost.train()` | Can be called from the training script |

Script mode still uses the AWS-managed SageMaker XGBoost image, Training Job, S3 input channels,
and model output as-is. No custom Docker image is required. The only difference is that, inside
the container, this repository's `autolog.py` runs instead of AWS's built-in training code.

The existing `train.py` demonstrates built-in algorithm mode with explicit MLflow logging, so it
is kept unchanged. Looking at the two examples together makes the difference clear.

- `train.py`: training uses the built-in algorithm, and local code performs MLflow logging explicitly
- `train_autolog.py`: local code only starts the Job, and the cloud training script logs automatically

## Why use XGBoost 3.0-5?

The existing built-in example uses XGBoost `1.7-1`. However, the officially supported range for
XGBoost autolog in MLflow `3.10.1` is XGBoost `2.1.0` through `3.2.0`.

Of the versions SageMaker officially supports in framework mode, `3.0-5` falls within this range,
so it is used only for the autolog example. The XGBoost version for the whole project was not
changed across the board, to avoid abruptly changing the results or model versions of the
existing examples.

## Roles of the two Python files

### `train_autolog.py`: local launcher

Runs on your local machine.

1. Prepares the public dataset.
2. Uploads the train/validation CSVs to S3.
3. Passes the training script and requirements with SDK v3 `SourceCode`.
4. Runs the Training Job with SageMaker `ModelTrainer`.

### `autolog.py`: cloud training script

Runs inside the SageMaker Training instance.

1. Reads the feature order created by local data preparation from `SM_CHANNEL_METADATA`.
2. Reads the CSVs from `SM_CHANNEL_TRAIN` and `SM_CHANNEL_VALIDATION`.
3. Sets the managed MLflow App ARN as the tracking URI.
4. Enables `mlflow.xgboost.autolog()`.
5. Trains with `xgboost.train()`.
6. Saves the model with the best validation AUC to `SM_MODEL_DIR`.

SageMaker automatically provides the `SM_CHANNEL_*` and `SM_MODEL_DIR` environment variables.
Files under `SM_MODEL_DIR` are compressed into `model.tar.gz` and uploaded to S3 after the Job
finishes. Autolog is enabled before the `DMatrix` is created so that it can capture the input
example and signature.

`data-summary.json` is generated by `data_prep.py` with the actual feature names and order.
As a result, features are not hard-coded again in the cloud training script.

## What is logged automatically

Once autolog is enabled before `xgboost.train()`, the following items are recorded in the MLflow
run.

| MLflow item | Values shown in the example |
|---|---|
| Parameters | objective, eta, max depth, subsample, etc. |
| Metrics | train AUC and validation AUC per boosting round |
| Artifacts | feature importance JSON and plot |
| Logged Model | XGBoost model |
| Model metadata | input example and inferred signature |

What the code adds explicitly are SageMaker context tags such as the SageMaker Training Job name,
instance type, image URI, dataset ID, and S3 URIs. Autolog records the model, the XGBoost training
parameters, and per-iteration metrics. Only the best early-stopping AUC and the
`early_stopping_patience` value are added
as a final summary to make comparison across runs easier.

`validation-auc` uses the same name as in the existing built-in Training and AMT runs. When early
stopping finishes, the best AUC is logged once as the last point of the same metric, so you can
directly compare each run's final value in MLflow Compare.

The MLflow run tags also record the exact S3 URIs of the train CSV, validation CSV, and data
summary. Even without S3 versioning or a separate hash, the SageMaker Training Job's input
channels and the MLflow run can be linked by the same URIs.

## Run

If you have just created the infrastructure or after adding this example, you need to apply the
MLflow API permissions to the Training role.

```bash
./scripts/bootstrap-infra.sh
./scripts/run-autolog-training.sh
```

To use a different CPU Training instance, run the following.

```bash
./scripts/run-autolog-training.sh --instance-type ml.m6i.xlarge
```

If you specify a G4dn or G5 instance, the script checks the number of GPUs reported by SageMaker
and uses XGBoost `device=cuda`. For the 30,000-row sample, CPU is more cost-effective.

The following steps appear during the run.

```text
[1/3] Prepare the public dataset and upload it to S3
[2/3] Run the script-mode SageMaker Training Job
[3/3] Training and MLflow autologging complete
```

After completion, open the `sagemaker-xgboost-lab` experiment in the MLflow App and select the
`autolog-<run-id>` run.

## When a startup should choose this approach

Script mode with autolog is convenient under the following conditions.

- The team already has open-source XGBoost code
- You want to record parameters and per-iteration metrics without missing any
- Preprocessing or custom evaluation needs to live inside the training code
- You do not yet have requirements that justify managing a custom image

If you do not need training code and just want to quickly run SageMaker's default CSV training,
the existing built-in algorithm mode is shorter. There is no need to convert all existing Jobs to
script mode just for autolog.

## Things to know

When the Training Job starts, it installs the MLflow client and AWS plugin listed in
`autolog-requirements.txt`. In a private VPC without default internet access, you need a private
package repository or a custom image that includes the dependencies.

The purpose of this autolog example is experiment tracking. The MLflow Logged Models from the
existing `train.py` and `train_tunner.py` also explicitly record a SageMaker inference
specification for Batch Transform. Therefore, the Registry and Batch Transform exercises in this
repository continue to use the two existing flows.
