# Migration tools: where to look, how to see the SQL, and the traps

For each tool: where migrations live, how to see the SQL that will actually run, how to run a statement outside a transaction (needed for `CONCURRENTLY`), and the tool-specific traps worth flagging.

Tool behavior changes between versions. When a claim here matters to the verdict, confirm it against the project's installed version: check the lockfile, the tool's docs, or a dry run against a local database. If you can't confirm it, say so in the report.

## Universal rules

- **Review the SQL, not the DSL.** Generate or print it with the commands below.
- **`CONCURRENTLY` can't run inside a transaction block.** That includes a tool's wrapping transaction, and a file sent to the server as one multi-statement string, which PostgreSQL runs as a single implicit transaction. Both fail loudly with `CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. Give each `CONCURRENTLY` statement **its own migration containing nothing else**, with the tool's transaction turned off.
- **Renames that became drop + add.** Autogenerated migrations often turn a renamed field into `DROP COLUMN` plus `ADD COLUMN`, which loses data silently. Flag any migration that drops and adds columns on the same table.
- **Never use schema "push" or "sync" against production** (`prisma db push`, `drizzle-kit push`, TypeORM `synchronize: true`, Sequelize `sync({ alter: true })`). They diff and apply directly, with no reviewable migration, and can drop columns.
- **Identify the transaction model**: one transaction per migration, one for all pending migrations, or none. It decides how long locks are held and whether a failure leaves a half-applied migration.

## Finding migrations in a diff

```bash
git diff --name-only origin/main...HEAD | grep -E \
  'prisma/migrations/.*\.sql$|migrations/app/.*/(migration\.ts|ops\.json)$|drizzle/.*\.sql$|db/migrate/.*\.rb$|/migrations/[0-9].*\.py$|alembic/versions/.*\.py$|migrations/versions/.*\.py$|migrations?/.*\.(js|ts)$|db/migration/V.*\.sql$|changelog.*\.(xml|ya?ml|sql)$|\.up\.sql$|supabase/migrations/.*\.sql$|\.sql$'
```

Also check schema files that drive generated migrations: `prisma/schema.prisma`, `drizzle` schema `.ts` files, `models.py`, entity classes, and `db/schema.rb` or `db/structure.sql`.

## Prisma

These notes cover **Prisma ORM 7** and earlier (SQL migration files). Check the version in `package.json`. Prisma ORM 8, a release candidate as of November 2026, works differently; see the end of this section.

- **Files:** `prisma/migrations/<timestamp>_<name>/migration.sql`, generated from `prisma/schema.prisma`.
- **See the SQL:** it's the `migration.sql` file. To generate without applying, run `npx prisma migrate dev --create-only` (against a dev database), then edit the file before applying. Production applies with `npx prisma migrate deploy`.
- **Transactions and CONCURRENTLY:** Prisma 7.4+ sends each statement in `migration.sql` separately, with no wrapping transaction. Earlier versions, and any script Prisma's SQL parser can't split, run the whole file as one implicit transaction. Two consequences:
  - On 7.4+, a multi-statement migration **isn't atomic**. If a statement fails, the earlier ones stay applied.
  - To be safe on every version, put each `CREATE INDEX CONCURRENTLY` in its own `--create-only` migration with nothing else in the file, and add the matching `@@index` to `schema.prisma` so Prisma doesn't see drift.
- **Failed migrations block deploys.** A migration that fails (for example on `lock_timeout`) is recorded as failed, and `migrate deploy` refuses to continue (error P3009) until someone runs `prisma migrate resolve --rolled-back <name>` (or `--applied`). Make that part of the team's runbook before turning on `lock_timeout`.
- **Traps to flag:**
  - Generated `CREATE INDEX` and `CREATE UNIQUE INDEX` are non-concurrent. Generated foreign keys are validated immediately, which scans the table and blocks writes on both tables.
  - A renamed field becomes `DROP COLUMN` plus `ADD COLUMN`. Use `@map("old_column")` to rename in code only.
  - Defaults: `DateTime` maps to `timestamp(3)` without a time zone (prefer `@db.Timestamptz(3)`). `Int @default(autoincrement())` maps to `SERIAL`, a 32-bit int (prefer `BigInt`). `Float` maps to `double precision` (use `Decimal` for money).
  - Prisma doesn't create indexes on relation scalar fields for PostgreSQL. Add an `@@index([userId])` for each foreign key you join or delete by.
  - Model names are used as table names verbatim, so `model User` becomes a quoted `"User"` table. Use `@@map("users")` to keep plain snake_case SQL.
- **Prisma ORM 8 (release candidate):**
  - Migrations are folders under `migrations/app/<timestamp>_<name>/`, containing `migration.ts`, `ops.json`, and `migration.json`. There's no SQL file.
  - They're applied with `prisma db migrate`; `migrate dev` and `migrate deploy` are gone. To see the SQL, use `prisma migration plan` or `prisma migration show`.
  - On PostgreSQL, a `db migrate` run is one transaction. Its docs say `CREATE INDEX CONCURRENTLY` can't run inside a migration, so run concurrent index builds as a separate pipeline step.
  - Plain `DateTime` now defaults to `timestamptz(3)`.
  - Because this is still a release candidate, confirm the details against the Prisma 8 docs before relying on them in a verdict.

## Drizzle

- **Files:** the `out` directory in `drizzle.config.*` (commonly `drizzle/`).
  - drizzle-kit 0.x writes `NNNN_name.sql` files plus `meta/_journal.json`.
  - drizzle-kit 1.0 writes one folder per migration (`<timestamp>_<name>/migration.sql` and `snapshot.json`) with no journal.
  - Generate with `npx drizzle-kit generate`. Apply with `npx drizzle-kit migrate`, or `migrate()` from `drizzle-orm/<driver>/migrator`.
- **See the SQL:** the generated `.sql` file. Statements are separated by `--> statement-breakpoint`.
- **Transactions and CONCURRENTLY:** Drizzle's PostgreSQL migrator runs **all pending migrations in a single transaction**, with no option to disable it. So locks from the first migration are held until the last one commits, and a `CONCURRENTLY` statement in a migration file fails. Run concurrent index builds as a separate pipeline step (`psql` or a small script), and keep the schema file in sync.
- **Traps to flag:** `timestamp()` defaults to without time zone (use `timestamp({ withTimezone: true })`). `serial()` is a 32-bit int (use `bigserial` or `bigint(...).generatedAlwaysAsIdentity()`). `.references()` doesn't create an index. drizzle-kit asks interactively whether a change is a rename, so a wrong answer becomes drop plus add.

## Rails (Active Record)

- **Files:** `db/migrate/*.rb`, with `db/schema.rb` or `db/structure.sql`.
- **See the SQL:** run the migration against a local database and read the SQL in `log/development.log`. The `db:migrate` console output shows only the DSL calls and timings, not the SQL.
- **Transactions:** each migration runs in a transaction by default. Opt out with `disable_ddl_transaction!`.
- **Safe forms:**
  ```ruby
  class AddIndexOnOrdersUserId < ActiveRecord::Migration[7.1]
    disable_ddl_transaction!
    def change
      add_index :orders, :user_id, algorithm: :concurrently
    end
  end

  # foreign key: two migrations
  add_foreign_key :orders, :users, validate: false
  validate_foreign_key :orders, :users

  # check constraint (Rails 6.1+): two migrations
  add_check_constraint :orders, "total >= 0", name: "orders_total_non_negative", validate: false
  validate_check_constraint :orders, name: "orders_total_non_negative"
  ```
- **Traps to flag:**
  - `add_reference ... foreign_key: true` adds a non-concurrent index and a validated foreign key. Split it into `add_reference ... index: false`, `add_index ... algorithm: :concurrently`, then `add_foreign_key ... validate: false` and `validate_foreign_key`.
  - `change_column_null :t, :c, false` scans under ACCESS EXCLUSIVE. Use the CHECK pattern first (`add_check_constraint ... "c IS NOT NULL", validate: false`).
  - `remove_column` while models still cache the column breaks running code. Add `self.ignored_columns += ["col"]` and deploy that first.
  - `rename_column` breaks running code. Use `alias_attribute` instead.
  - The `datetime` type is `timestamp` without a time zone unless you configure `datetime_type = :timestamptz` (Rails 7+).
- **Lint:** the [strong_migrations](https://github.com/ankane/strong_migrations) gem catches most of this and can set `lock_timeout` for you.

## Django

- **Files:** `<app>/migrations/NNNN_*.py`.
- **See the SQL:** `python manage.py sqlmigrate <app> <migration_name>`. In CI, `python manage.py makemigrations --check --dry-run` catches missing migrations.
- **Transactions:** migrations are atomic on PostgreSQL by default. Set `atomic = False` on the `Migration` class to opt out.
- **Safe forms:**
  ```python
  from django.contrib.postgres.operations import AddIndexConcurrently
  from django.db import migrations, models

  class Migration(migrations.Migration):
      atomic = False
      dependencies = [("orders", "0041_previous")]
      operations = [
          AddIndexConcurrently("order", models.Index(fields=["created_at"], name="orders_created_at_idx")),
      ]
  ```
  `RemoveIndexConcurrently` is the reverse. For CHECK constraints, `AddConstraintNotValid` plus `ValidateConstraint` (Django 4.0+) give the NOT VALID pattern. For anything else, use `migrations.RunSQL(...)`, with `SeparateDatabaseAndState` to keep Django's model state in sync.
- **Traps to flag:**
  - A `ForeignKey` field gets an index by default (`db_index=True`), built with plain `CREATE INDEX`. On big tables, set `db_index=False` and add the index with `AddIndexConcurrently`.
  - `RemoveField` drops the column in the same release that removes the field, while old code may still select it. Remove it from state first (`SeparateDatabaseAndState`) and drop the column in a later release.
  - `RenameField` renames the database column. Use `db_column="old_name"` instead.
  - `RunPython` backfills run inside the migration transaction. Use `atomic = False` with batches, or a management command.
- **Lint:** [django-migration-linter](https://github.com/3YOURMIND/django-migration-linter), or the [django-pg-zero-downtime-migrations](https://github.com/tbicr/django-pg-zero-downtime-migrations) database backend.

## Alembic (SQLAlchemy, Flask-Migrate)

- **Files:** `alembic/versions/*.py`, or `migrations/versions/*.py` with Flask-Migrate.
- **See the SQL:** offline mode, `alembic upgrade <from_rev>:<to_rev> --sql`.
- **Transactions:** by default `env.py` runs all pending migrations in one transaction. Setting `transaction_per_migration=True` in `context.configure(...)` gives one transaction per migration.
- **Safe forms:**
  ```python
  def upgrade():
      with op.get_context().autocommit_block():
          op.create_index("orders_created_at_idx", "orders", ["created_at"], postgresql_concurrently=True)

      op.execute("ALTER TABLE orders ADD CONSTRAINT orders_user_id_fkey "
                 "FOREIGN KEY (user_id) REFERENCES users (id) NOT VALID")
  ```
  Put `VALIDATE CONSTRAINT` in the next migration, or in its own `autocommit_block()`.

  Entering `autocommit_block()` commits everything the run has done so far. With the default single-transaction `env.py`, that includes earlier migrations in the same run, committed partway through. Alembic recommends `transaction_per_migration=True` when you use autocommit blocks.
- **Traps to flag:** autogenerate can't detect column renames; it emits `drop_column` plus `add_column`. `op.alter_column(..., nullable=False)` is `SET NOT NULL`, a scan. `op.create_foreign_key` validates immediately.

## Knex

- **Files:** `migrations/*.{js,ts}`. Run with `knex migrate:latest`.
- **See the SQL:** run against a local database with `DEBUG=knex:query`.
- **Transactions:** despite the docs' wording, `migrate:latest` runs **all pending migrations in one transaction** by default, so the first migration's locks are held until the whole batch commits. If any pending migration sets `exports.config = { transaction: false };`, that one runs without a transaction and the others each get their own.
- **Traps to flag:** `table.index()` and `.foreign()` / `.references()` produce non-concurrent indexes and validated FKs. Use `knex.raw(...)` for the safe forms.

## TypeORM

- **Files:** the configured `migrations` directory, often `src/migrations/*.ts`. Generate with `typeorm migration:generate`. Apply with `migration:run`.
- **See the SQL:** the generated `up()` method contains raw SQL strings.
- **Transactions:** controlled by the data source's `migrationsTransactionMode`: `"all"` (the default, so one transaction for every pending migration), `"each"`, or `"none"`. A migration class can set `transaction = false`, but only with `"each"` or `"none"`. Under `"all"`, TypeORM refuses to run and throws `ForbiddenTransactionModeOverrideError`.
- **Traps to flag:** `synchronize: true` in a production data source is a red flag; it can drop columns. A renamed entity property generates drop plus add.

## Sequelize

- **Files:** `migrations/*.js` (sequelize-cli).
- **Transactions:** migrations don't run in a transaction unless you wrap them yourself.
- **Safe forms:** `queryInterface.addIndex("orders", ["created_at"], { concurrently: true })`, or `queryInterface.sequelize.query("...")` for NOT VALID constraints.
- **Traps to flag:** `sequelize.sync({ alter: true })` or `{ force: true }` in production code.

## Flyway

- **Files:** `db/migration/V<version>__<description>.sql`, often under `src/main/resources/`.
- **Transactions:** each PostgreSQL migration runs in its own transaction by default.
  - Flyway detects `CREATE INDEX CONCURRENTLY` and runs that script outside a transaction. You can also set `executeInTransaction=false` in a `<script>.sql.conf` file.
  - It rejects scripts that mix transactional and non-transactional statements unless `mixed=true`, so keep each `CONCURRENTLY` statement in its own file.
  - Also set `flyway.postgresql.transactional.lock=false`. Redgate documents that the default transactional advisory lock causes problems with `CREATE INDEX CONCURRENTLY`.
- **See the SQL:** the files themselves.

## Liquibase

- **Files:** changelogs (`db/changelog/*.xml|yaml|sql`).
- **See the SQL:** `liquibase update-sql`.
- **Transactions:** each changeset runs in a transaction. Set `runInTransaction="false"` (or `runInTransaction:false` in SQL-format changelogs) for `CONCURRENTLY` changesets.

## golang-migrate, dbmate, Supabase CLI, and raw SQL files

- **Files:** `NNNN_name.up.sql` / `.down.sql` (golang-migrate), `db/migrations/*.sql` (dbmate), `supabase/migrations/*.sql`.
- **Transactions:** these tools vary. Some send the whole file as one multi-statement string, which runs as a single implicit transaction, so put each `CONCURRENTLY` statement in a file of its own. dbmate wraps each migration in a transaction unless you add `-- migrate:up transaction:false`. For any tool not listed, assume a transaction and confirm with a dry run against a local database: a misplaced `CONCURRENTLY` fails loudly, not silently.
- **`psql -f file.sql`** runs each statement separately in autocommit mode, unless the file has `BEGIN`/`COMMIT` or you pass `--single-transaction`.
