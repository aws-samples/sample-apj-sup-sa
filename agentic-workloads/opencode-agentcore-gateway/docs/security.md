# Security

This page describes what the sample protects, how, and where in the code each control lives. It is not a substitute
for your own security review before you put real users on the stack.

## What is protected

| Asset | Why it matters |
|---|---|
| AWS spend on Amazon Bedrock | Anyone who can call a model spends the account's money |
| Which models a person may use | Teams may be limited to approved models |
| Prompts and code sent to the model | Developers send source code |
| The developer's IdP refresh token | Lets the holder mint new tokens until it is revoked |
| The admin dashboard | Changes budgets, limits and model access |

## Trust boundaries

1. **Laptop to gateway.** HTTPS with the developer's IdP token. No AWS credentials on the laptop.
2. **opencode to the local proxy.** Loopback only, with a per-machine key.
3. **Gateway to Amazon Bedrock.** The gateway's IAM role; callers never hold Bedrock permissions.
4. **Admin to dashboard.** By default an IAM-authorized Lambda Function URL (SigV4; viewer role unless `dashboard_private_role` is admin); optionally an ALB with IdP sign-in, admin or viewer group, HTTPS, IP allow-list.

## Controls

| Threat | Control | Where |
|---|---|---|
| Call without a valid token | Gateway JWT authorizer checks signature, issuer, expiry and audience or client ID | `terraform/gateway.tf`, `terraform/identity.tf` |
| Token the gateway accepted but the interceptor reads differently (two `Authorization` headers, extra words) | Interceptor refuses anything but exactly one `Bearer <jwt>` header | `lambda/interceptor.py` `claims_of` |
| Using a model the group may not use | Group allow-list on every call; `/v1/models` lists only allowed models | `lambda/interceptor.py`, `lambda/policy.py` |
| Fallback serving a model the caller may not use | Terraform refuses a chain unless every group allowed the primary is allowed each fallback model; the interceptor re-checks the chain against the caller on every call, so later dashboard edits cannot open it | `terraform/fallback.tf`, `lambda/interceptor.py` `FALLBACKS` |
| Spending past a budget | Monthly, daily and hourly caps checked before each call; web search charged up front | `lambda/interceptor.py` `spend`, `charge_search` |
| Request floods | Gateway rate limits (RPM and TPM per user) plus the interceptor's per-user rpm counter | `terraform/policy.tf`, `lambda/interceptor.py` `take_rpm` |
| Signing in under another user's budget by choosing a claim value | Okta and JumpCloud key on the immutable `sub` through a required `identity_map`; unmapped ids are refused | `lambda/interceptor.py` `ledger_user` |
| Pretending to be another user's project (cost shifting) | Client-sent `OpenAI-Project`, `OpenAI-Organization` and `x-ocgw-*` headers are dropped and set by the interceptor | `lambda/interceptor.py` `INJECTED` |
| Bodies that parse differently downstream (duplicate keys, `NaN`, `1e999`, deep nesting) | Parsed once, refused if not strict JSON, forwarded as re-serialised | `lambda/interceptor.py` `http_handler` |
| Path tricks (`%2F`, double encoding, `..`, unknown routes) | Only four routes are accepted (chat completions, responses, models, and `/inference/websearch`, which the interceptor answers itself), matched on the path AgentCore has already decoded once; a `%` still in it, `..`, `//` or anything else is 404 | `lambda/interceptor.py` `route_of` |
| An unexpected error letting a request through | Interceptor fails closed with a generic error; detail stays in the log | `lambda/interceptor.py` `lambda_handler` |
| Another local user or a web page using the proxy | Proxy binds 127.0.0.1 only and needs the 0600 per-machine key; constant-time comparison | `client/ocgw.py` `proxy`, `local_key` |
| Proxy used to reach other hosts | Proxy forwards only to the configured HTTPS gateway and web search URLs, only the listed paths, bodies up to 32 MiB | `client/ocgw.py` `FORWARD` |
| Refresh token sent to an attacker's issuer (a repo's `.env` setting `OCGW_OIDC_ISSUER`) | MDM config is read last and wins over environment and user config; HTTPS only | `client/ocgw.py` `config`, `https` |
| Sign-in code intercepted by a page that hits the loopback port | PKCE (S256) and a random `state`; requests without the state get 404 | `client/ocgw.py` `login` |
| Two refreshes spending the same rotating refresh token | File lock around read-refresh-save; tokens written 0600 and atomically | `client/ocgw.py` `token_lock`, `save` |
| Data at rest | Ledger, Lambda environment and log groups encrypted with a customer managed KMS key with rotation | `terraform/security.tf`, `terraform/ledger.tf` |
| Over-broad IAM | Each Lambda role is scoped to its table and actions; the interceptor may update only `USER#` items and listed attributes | `terraform/policy.tf` |
| Dashboard access | Function URL (default): `AWS_IAM` (SigV4), every caller at `dashboard_private_role` (default viewer), lowered to viewer by `x-ocgw-client: read-only-proxy`. ALB (optional): `authenticate-oidc`, admin or viewer group check on the signed ALB header (ES256, signer ARN, expiry), admin for writes. Both: CSRF header and origin check on writes, audit rows added in the same transaction, each Put conditioned on `attribute_not_exists(sk)` (r192), actor `<email> (<sub>)` from r194. | `terraform/dashboard_alb.tf`, `terraform/dashboard.tf`, `lambda/dashboard.py` |

## Known limits

- Budgets are enforced from metrics that lag by a few minutes, so a user can overshoot a cap by a few minutes of traffic.
- The local proxy trusts every process of the signed-in OS user that can read the key file, which is the same trust a
  token cache file has.
- The gateway's `bedrock-mantle` connector uses the gateway IAM role; Mantle project tags are what attribute usage per
  user.
- The groups the dashboard shows for a user are the groups on the newest token the gateway has seen. A user who
  keeps an older token in use after an IdP change cannot move the record back, but a re-created BUDGET item shows
  the seeded group until the user's next token, about an hour.

## Review decisions

trade-off instead of reopening it.

| Round | Finding | Decision |
|---|---|---|
| r137 | Record a user's groups in the background window writes instead of an ordered write on BUDGET | Kept. Window items are per period and per model, so the dashboard and usage_sync would need a new "latest groups" reader across them, and the background writes are the ones Lambda can finish after the reply (the r128 bug). The ordered write is one conditional write per user per new token. |
| r137 | An HTTP web search that ends in `websearch_error` may record the groups its MCP call already recorded | Kept. The HTTP side cannot tell whether the MCP call ran; recording again costs one conditional write that is refused, while skipping would lose the record when the MCP call never ran. |
| r137 | On MCP the groups write runs after the gate instead of beside it | Kept. The MCP path's pool slots are taken by the search charge's three window writes; the write happens only once per user per new token. |
| r139 | A chat scenario's one retry makes a second billed call that other scenarios do not account for | Kept. A retry happens only when a model answers without PONG, which is rare; the rate-limit scenarios start at a fresh minute and clear that minute's counter, and no scenario asserts a user's exact request total. | r140 | Group, tag and summary rollups count an unreadable web search spend as $0 while the user's row shows blocked | Kept.
