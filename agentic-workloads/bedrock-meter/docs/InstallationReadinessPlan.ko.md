# 첫 설치 준비도 개선 설계

> 상태: 코드 구현과 macOS 로컬 검증 완료. 실제 AWS 신규 설치와 Linux 실행 검증은 대기 중입니다.
> 리뷰 기준일: 2026년 11월 25일.
> 범위: 처음 내려받은 사람이 README를 따라 설치하고 첫 사용량을 확인하기 위한 최소 개선.

## 1. 목표와 검증 기준선

첫 공개의 목표는 **깨끗한 checkout → 배포 → 관리자 생성 → 로그인 → 사용량 확인**이라는
한 가지 경로를 끝까지 동작시키는 것입니다. 기존 일곱 리뷰 항목은 유지하되, 범용 배포 도구나
자동 복구 기능으로 확대하지 않습니다. 현재 설치 안내는 [README](../README.ko.md)에 있습니다.

이전 리뷰에서 두 `npm ci`, 콘솔 전체 빌드, TypeScript 컴파일, CDK synth와 테스트 111개가
통과했습니다. 환경은 macOS, Node.js 22.22.3, Python 3.14.2였습니다. 새 복사본에서 bootstrap
순서 오류를, 모의 AWS 호출에서 리전 전달 문제를, 실제 운영 빌드에서 개발 API 주소 포함을
확인했습니다. 이는 변경 전 기준선이며 실제 AWS 신규 설치·로그인 성공을 증명하지 않습니다.
재설치 충돌은 코드 검토 결과이며 실제 복구 절차 검증은 별도로 필요합니다.

## 2. 첫 공개에 포함할 범위

| 리뷰 항목 | 이번에 구현할 내용 |
|---|---|
| 1. Bootstrap 순서 | 실제 콘솔 빌드 후 bootstrap과 배포 실행. |
| 2. 배포 리전 | 터미널/profile의 AWS 대상을 확인하고 후속 명령에 같은 리전 전달. 일반 설치에서 backfill 제거. |
| 3. 첫 관리자 | 배포와 같은 설정으로 사용자 풀 조회와 사용자 생성. |
| 4. 운영 API 주소 | Production은 same-origin으로 고정, 개발 override는 development에서만 사용. |
| 5. 의존성 | 호환되는 버전과 lockfile로 설치·빌드 검증, 중요한 취약점 처리. |
| 6. 런타임 | 지원되는 Node.js 런타임과 빌드 환경으로 정렬. |
| 7. 실패와 재시도 | 실패 단계·원인 표시와 수동 복구 안내. 자동 삭제 없음. |

한도, 집계, IAM 차단 의미, 데이터 모델, 리소스 이름과 삭제 정책은 변경하지 않습니다.
배포·계정 관리 스크립트에 새 `--account`, `--region`, `--profile`, `--stack` 옵션이나
범용 설정 파서는 만들지 않습니다. 수동 backfill도 현재 AWS 실행 대상을 사용합니다.

## 3. 항목 1: 설치 순서

최초 배포는 `scripts/deploy-all.sh --bootstrap`을 사용합니다. 옵션 없는 명령은 기존처럼
재배포에 사용합니다. 두 경로를 README에 반영했습니다.

실행 순서는 다음과 같습니다.

1. 필요한 도구와 버전을 확인하고, 터미널/profile에서 AWS 계정·리전을 확정합니다. 프로젝트 설정을 읽되 AWS 대상은 변경하지 않습니다.
2. 두 프로젝트에서 `npm ci`를 실행하고 콘솔 정적 파일과 BFF를 한 번 빌드합니다.
3. `--bootstrap`이면 확정한 계정·리전으로 CDK bootstrap을 실행합니다.
4. 같은 대상에 stack을 배포하고 출력값을 확인합니다.
5. 콘솔 URL, 관리자 생성 명령, SNS 이메일 확인을 다음 작업으로 안내합니다.

콘솔 산출물 누락 검사는 유지합니다. 빌드 실패 시 AWS 변경 전에 중단하고, bootstrap 실패 시
배포하지 않습니다. Bootstrap 호환성을 자체 판정하는 진단 기능은 만들지 않고 CDK 오류를
보존합니다. 오류에는 실패 단계와 다음에 확인할 문서 위치를 덧붙입니다.

통합 경로가 구현되어 별도 bootstrap과 중복 빌드를 안내하지 않습니다. 직접 CDK 명령을 쓰는
개발자는 콘솔 산출물을 먼저 빌드해야 합니다.

**변경 대상:** [`deploy-all.sh`](../scripts/deploy-all.sh), 두 언어의 README와
[CDK README](../cdk/README.ko.md).

## 4. 항목 2·3: 하나의 설정과 같은 배포 대상

### AWS 대상과 프로젝트 설정

계정·리전은 프로젝트 파일에 다시 입력하지 않습니다. `deploy-all.sh`와 `_add-console-user.sh`는
같은 짧은 함수로 현재 터미널의 AWS 실행 대상을 확인합니다.

- **계정:** 현재 자격증명으로 `aws sts get-caller-identity`를 호출해 실제 계정을 확인합니다.
  `CDK_DEFAULT_ACCOUNT`를 사용자 입력으로 사용하지 않습니다.
- **리전:** 비어 있지 않은 `AWS_REGION` → `AWS_DEFAULT_REGION` → 현재 선택된 AWS profile의
  리전 순으로 결정합니다. 환경변수에 리전이 없으면 같은 AWS CLI 설정으로 profile의 리전을
  조회합니다. Profile 설정 파일을 직접 파싱하지 않습니다.
- **미설정·오류:** 리전이 없으면 설정 방법을 안내하고 중단합니다. 서울로 임의 지정하지 않습니다.
  자격증명 만료, 사용할 수 없는 profile, STS 실패도 변경 전에 중단합니다.
- **자격증명:** `AWS_PROFILE`을 포함한 현재 AWS 자격증명 설정을 유지합니다. 별도의 자격증명
  선택기나 교차 계정 배포 기능은 추가하지 않습니다. Profile 이름만으로 계정을 추정하지 않습니다.
- **일관성:** 실행 초기에 확정한 계정·리전을 출력합니다. Bootstrap과 배포에 같은 대상을 사용하고,
  리전별 AWS CLI 명령에는 확정한 `--region`을 전달합니다. CDK에 필요한 `CDK_DEFAULT_ACCOUNT`와
  `CDK_DEFAULT_REGION`은 이 결과에서 내부적으로 설정하며, 외부의 기존 값으로 대상을 바꾸지 않습니다.

`.env.deploy.example`과 `.env.deploy.local`에는 관리자 이메일·사용자명, quota timezone,
기능 flag 같은 프로젝트 설정만 둡니다. 계정·리전과 AWS 자격증명/profile은 이 파일에서 설정하지
않습니다. 기존 `BEDROCK_METER_DEPLOY_ENV_FILE` 선택과 환경변수 전용 실행은 유지합니다.
파일은 기존처럼 신뢰된 로컬 shell 설정으로 취급하며 별도 설정 형식은 도입하지 않습니다.

설정 예제에서 `CDK_DEFAULT_ACCOUNT`와 `CDK_DEFAULT_REGION`을 제거하고, 기존 파일의
계정·리전 항목을 지우고 AWS 터미널/profile 설정으로 옮기는 전환 안내를 제공합니다.
프로젝트 파일이 AWS 자격증명·profile·리전을 덮어쓰도록 지원하지 않습니다.
기존 `CDK_DEFAULT_*`와 관리자 스크립트의 `REGION`은 배포 대상 선택에 사용하지 않습니다.

각 명령은 실행 시점의 터미널 설정을 사용합니다. 나중에 다른 터미널에서 관리자 생성이나
재배포를 실행하면 같은 AWS 계정·리전이 선택되어 있어야 합니다. 출력되는 대상을 확인하도록
안내하되, 로컬 출력 파일로 자격증명이나 리전을 조용히 바꾸지 않습니다.

### 첫 관리자

기존 admin/viewer wrapper와 숨김 비밀번호 입력을 유지합니다. 같은 계정·리전의 실제 stack
출력에서 사용자 풀을 조회합니다. 조회 실패를 오래된 `cdk-outputs.json`으로 숨기는 fallback은
제거합니다. 기존 명시적 `POOL_ID` 입력은 유지하되, 사용 전 pool의 계정·리전을 확인합니다.
Pool 확인 실패나 리전 불일치는 사용자 변경 전에 중단합니다.

### Retention backfill

기존 데이터의 보존 기간을 연장하는 Python 스크립트는 배포 과정에서 제외하고, 보존 정책 변경 시에만
별도로 실행합니다. 현재 AWS 자격증명과 위 리전 우선순위를 사용하며, 리전 미설정 시 중단합니다.
운영 문서에서 실행 전 계정·리전과 대상 테이블을 확인하도록 안내하고, 재배포만으로 과거 행의
보존 기간이 바뀌지 않음을 명시합니다.
새 shell wrapper, 중복 계정 검증 체계, 동시 갱신 재시도 기능은 이번 설치 개선에 포함하지 않습니다.

**변경 대상:** [`deploy-all.sh`](../scripts/deploy-all.sh),
[`_add-console-user.sh`](../scripts/_add-console-user.sh), 작은 공통 설정 helper,
[`backfill-retention.py`](../scripts/backfill-retention.py), 설정 예제와 관련 문서·테스트.

## 5. 항목 4: 운영 API 주소

[`api.ts`](../client/app/src/lib/api.ts)에서 production은 `/api/console`을 사용하도록 고정합니다.
`NEXT_PUBLIC_CONSOLE_API_BASE`는 development에서만 읽습니다. 설정 조회도 같은 API base를
사용하므로 운영은 same-origin, 개발은 기존 원격 BFF 연결을 유지합니다.

배포 shell에서만 변수를 지우는 방법은 사용하지 않습니다. `.env.local`이 있거나 package build를
직접 실행해도 운영 산출물에 개발 호스트가 포함되지 않아야 합니다. 프로세스 변수와 `.env.local`을
각각 사용하는 빌드 검증으로 확인합니다.

**변경 대상:** `src/lib/api.ts`, 필요한 테스트, 두 언어의 [콘솔 README](../client/app/README.ko.md).

## 6. 항목 5·6: 의존성과 런타임

Manifest와 lockfile을 함께 갱신하고 `npm ci`로 설치합니다. 강제 audit fix나 peer dependency
검사 우회로 맞추지 않습니다. 호환되는 패치·마이너 갱신부터 검토하고, 필요한 major 변경은 별도로
빌드와 테스트를 확인합니다. 정확한 버전은 구현 시점의 공식 릴리스와 advisory로 결정합니다.

High/critical 항목은 수정하거나 적용되지 않는 근거를 기록합니다. 배포되는 정적 UI·BFF와
개발 서버·빌드 도구를 구분하되 개발 도구의 위험도 무시하지 않습니다. 미해결 항목은 원인과
후속 조치를 기록하여 공개 여부를 판단하고, audit 실행 실패를 취약점 없음으로 처리하지 않습니다.
별도 승인 시스템이나 모든 의존성에 대한 장문의 예외 문서는 만들지 않습니다.

Node.js 24를 목표로 콘솔 Lambda, esbuild target, 개발·검증 환경과 도구 버전 안내를 맞춥니다.
구현 시 [AWS 지원 런타임](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtimes.html)을
재확인합니다. Python Lambda는 변경하지 않습니다. Lambda construct ID를 유지하며 런타임을
제자리 갱신합니다. BFF의 런타임 제공 AWS SDK 의존성은 실제 배포 후 인증·Core API 호출로 확인합니다.

**변경 대상:** 두 `package.json`과 lockfile, [`console-hosting.ts`](../cdk/lib/constructs/console-hosting.ts),
[`build.mjs`](../client/app/bff-lambda/build.mjs), 도구 버전 안내와 검증 설정.

## 7. 항목 7: 실패 안내와 수동 복구

사전 검사는 필요한 도구, 자격증명·대상 계정, 대상 stack의 명백한 재시도 장애로 한정합니다.
Stack 작업 진행 중이나 `ROLLBACK_COMPLETE`이면 중단하고 상태에 맞는 안내를 출력합니다.
전체 리소스 목록을 돌며 소유권·고아 리소스·로깅 대상의 관계를 사전에 판정하지 않습니다.
나머지 배포 판단은 CDK와 기존 custom resource에 맡기고 실제 오류를 보존합니다.
조회 실패를 stack 부재로 간주하지 않습니다.

[OperationalGuide](OperationalGuide.ko.md)에 다음 실패의 확인 명령과 수동 처리 순서를 적고
README에서 연결합니다.

- Bootstrap 누락 또는 권한 부족: 원인을 해결한 후 해당 단계 재실행.
- `ROLLBACK_COMPLETE`: 실패 이벤트 확인 → 필요한 데이터 확인 → 운영자가 실패 stack 수동 삭제
  → 남은 리소스 확인 → 충돌 해결 후 재배포.
- 고정 이름 리소스 충돌 또는 기존 Bedrock 로깅 충돌: 대상·소유자·보존 필요성을 확인한 뒤
  운영자가 처리. 재사용·보존해야 하는 리소스라면 삭제 경로 중단.
- 관리자 생성 실패: 계정·리전·사용자 풀과 원래 오류를 확인한 뒤 해당 명령 재실행.

Stack 삭제 후 보존된 리소스가 남을 수 있음을 설명합니다. 비어 있지 않은 bucket 정리나
기존 로깅 변경은 운영자가 영향과 데이터 보존 필요성을 판단한 후 수동으로 수행합니다.
스크립트는 리소스를 자동 삭제하거나 로깅을 덮어쓰지 않습니다. 기존 삭제 정책과 로깅 Lambda의
삭제 동작도 변경하지 않습니다. 이 항목은 복구 도구가 아니라 오류 안내와 문서 개선입니다.

## 8. 구현 순서와 첫 공개 완료 기준

1. Bootstrap 순서의 문서 수정과 운영 API 주소 수정을 독립적으로 진행합니다.
2. 짧은 공통 AWS 대상 확인, 프로젝트 설정 로딩, 리전 전달, 관리자 생성과 backfill 분리를 구현합니다.
3. `--bootstrap` 설치 경로, 오류 안내와 수동 복구 문서를 마무리합니다.
4. 의존성·런타임 갱신은 별도 변경으로 검증하고, 최종 코드를 다음 기준으로 확인합니다.

| 필수 검증 | 완료 기준 |
|---|---|
| 깨끗한 로컬 설치 | 기존 설정·의존성·생성 파일 없이 README의 도구 버전으로 `npm ci`, 전체 빌드, 테스트와 synth 통과. 지원한다고 명시한 OS에서 확인. |
| 대상 일관성 | 환경변수만 있는 경우와 profile에만 리전이 있는 경우 모두 같은 대상으로 bootstrap·배포·관리자 생성. `AWS_REGION` 우선순위, 리전 미설정·자격증명 실패 시 중단, 기존 `CDK_DEFAULT_*` 입력이 대상을 바꾸지 않음을 확인. |
| 실제 최초 설치 | 서울과 비서울 리전에서 문서만으로 bootstrap → 배포 → 첫 관리자 생성 → 로그인 성공. 기존 배포 산출물이나 사용자 풀에 의존하지 않음. |
| 기능 확인 | 통제된 Bedrock 호출의 사용자·사용량 표시, SNS 구독 확인, admin/viewer 권한, 기본 통계 조회 확인. |
| 재배포 | 기존 사용자·데이터 유지, backfill 미실행, 개발 설정이 남아 있어도 운영 API는 same-origin 유지. |
| 실패 안내 | 모의 명령으로 단계별 실패, AWS 대상 확인 실패, 사용자 풀의 대상 불일치 시 중단을 확인. 복구 문서의 명령·대상·보존 주의사항을 실제 코드와 대조. |
| 의존성·런타임 | 중요한 audit 결과 검토, 선언한 런타임으로 배포 후 인증·API 호출 성공. |

테스트용 AWS 계정은 재사용할 수 있습니다. 기존 배포의 도움을 받지 않는 깨끗한 대상 환경이
필요하며, 검증마다 새 계정을 만들 필요는 없습니다. 고정 BFF IAM 역할 이름이 충돌하지 않도록
별도 테스트 계정을 사용하거나, 같은 계정에서는 이전 설치를 정리한 뒤 순차 검증합니다.
정리는 운영자가 수행하며 테스트 절차가 운영 데이터를 자동 삭제해서는 안 됩니다.

검증한 revision, 도구 버전, 계정·리전과 결과를 간단히 기록합니다. 전체 실패 주입 행렬이나
모든 재설치 예외 검증은 첫 공개의 필수 조건으로 두지 않습니다. 발견한 제한은 문서에 남깁니다.
두 언어의 README에는 하나의 주 설치 경로를 제공하고, 복구·수동 backfill은 운영 문서로 분리합니다.

## 9. 후속 작업

다음은 실제 운영에서 필요할 때 별도로 설계하며 첫 공개를 막지 않습니다.

- 다중 stack·교차 계정·사용자 지정 bootstrap 지원과 추가 CLI 옵션.
